# DiskFleet integration contract

This contract belongs to `modules/storage/` in the unified `pulsar-operator` repository. All code, UI and deployment paths below are relative to the repository root. Module documentation describes interface contracts; cross-module fixtures live in `test/fixtures/pulsar-storage`, and module scripts provide build and test entrypoints.

Storage API/tools: Go 1.26 in the root module (`cmd/storage-api`, `cmd/storage-plan`, `internal/storage`). The shared React console is built from `web/src` into `web/dist`; both API images serve that build. Storage standalone mode declares its API location through non-secret HTML metadata. The production node Agent is Go (`cmd/agent`, `internal/agent`) with its image in `modules/agent` and deployment in `config/agent`. Production storage uses OpenEBS LVM LocalPV CSI (`local.csi.openebs.io`), thick provisioning by default, `Retain`, `WaitForFirstConsumer`. Our Go per-node Agent discovers disks and creates/reconciles Volume Groups; CSI owns LVs/filesystems/mounts. No custom CSI protocol implementation.

API field names camelCase. Lists: `{items: [], total: int, limit: int, offset: int}`. Errors JSON `{detail: string}`. API auth: optional token in demo, required bearer token in cluster. UI sessionStorage token entered by user; no baked-in secrets.

The endpoint paths below are served directly by the storage API. The unified gateway exposes them under `/storage/api/` and removes `/storage` before forwarding; `/api/` on the gateway belongs to the Pulsar API. The two applications retain separate sessionStorage token keys.

- GET /api/config: `{mode: "demo"|"cluster", tokenRequired: bool}`
- GET /api/overview: `{mode, totals: {nodes,disks,pools,volumes,capacityBytes,allocatedBytes,availableBytes}, recentEvents:[], alerts:[]}`
- GET /api/nodes: all Kubernetes Nodes, including nodes without an Agent or disks; paginated `{name,uid,resourceVersion,zone,state,ready,unschedulable,enrolled,agentStatus,canEnableAgent,enableReasons:[],canCreatePool,reasons:[],disks,capacityBytes,allocatedBytes,mode}`. Agent status is `NotInstalled|NotEnrolled|Pending|Running|Unavailable`.
- GET /api/nodes/{name}?limit=50&offset=0: `{node,disks:{items,total,limit,offset}}`; disk filters `state` and `q` are supported.
- POST /api/nodes/{name}/agent `{uid,resourceVersion}` -> updated node. Validates the installed `diskfleet-system/diskfleet-agent` DaemonSet and node eligibility, then atomically adds the node enrollment label. It never changes the disk-write switch or creates arbitrary workloads; accepted enrollment is distinct from a Running Agent.
- GET /api/disks?q=&node=&state=&limit=50&offset=0: `{id,name,node,path,serial,sizeBytes,media,model,state,reasons:[],poolId}`; state Available/Managed/Protected/Offline. Additional fields: `uid,resourceVersion,nodeUID,lastObservedTime,validUntil,fresh,canCreatePool`; `reasons` includes the current admission blockers.
- GET /api/pools: paginated pool objects `{id,uid,resourceVersion,initializationApproved,deletionTimestamp,name,node,nodeUID,devices,vgName,capacityBytes,allocatedBytes,availableBytes,state,diskIds:[],storageClass,topologyHostname,createdAt,benchmark,allocationApproval,allocationState,canReview,canCreateVolume,allocationReasons:[]}`.
- GET /api/pools/{id}: one complete pool object, using the current Node UID and actual StorageClass.
- POST /api/pools/{id}/review `{uid,resourceVersion,runID,resultDigest,decision:"Approved"|"Rejected",note?}` -> updated pool. A rejection requires a nonblank note; notes are at most 1024 characters. `reviewedAt` comes from the server. UID/resourceVersion and the exact benchmark are rechecked before an optimistic patch. A committed audit intent precedes the patch; its outcome is recorded separately. `Rejected` may later become `Approved`; an existing `Approved` decision cannot be revoked or rewritten.
- POST /api/pools/plan `{name,node,diskIds:[]}` -> `{planId,expiresAt,commands:[],warnings:[],confirmation,disks:[]}`
- POST /api/pools `{planId,confirmation}` -> pool; demo simulated benchmark completes into AwaitingReview, cluster starts Pending. Both planning and creation revalidate Node health, the current DaemonSet-owned Ready Agent Pod, disk availability/ownership, Node and PhysicalDisk UIDs, and successful scan freshness. Expired or missing observations fail closed. An existing identical request remains idempotent.
- GET /api/volumes: `{id,name,namespace,poolId,pool,node,sizeBytes,status,storageClass,pvName,mountPath,createdAt}`
- Cluster volume responses additionally expose `pvcUid`, `management: diskfleet|external`, `canManage: bool`, `owners: [{kind,name,uid}]`, `bindingVerified: bool`, and `bindingMessage: string`. Bound volume location comes from the actual PV claim UID, CSI VG and node affinity; an unverified binding is read-only with an explanatory message. Pending volumes have no verified binding yet. External operator claims using verified DiskFleet classes are observable but never directly expanded/released. A Pulsar managed-by label is authoritative even if Retain leaves no ownerReferences. Shared classes use `storage.diskfleet.io/fleet=true` and a `storage.diskfleet.io/pool-uids` JSON annotation; see `internal/storage/fleet` and `internal/storage/cluster/resources.go`.
- POST /api/volumes `{name,namespace,poolId,sizeGiB}` -> volume; demo Bound (simulated), cluster Pending PVC. New allocations require a successful complete benchmark with verified cleanup, matching immutable approval, Ready state and the expected published StorageClass. Cluster mode re-reads the pool and current Node identity on submission. A Ready flag or client-supplied boolean is insufficient.
- POST /api/volumes/{id}/expand `{sizeGiB}` -> volume
- DELETE /api/volumes/{id}?uid={pvcUid}: cluster clients send the UID they confirmed. Retain only; no data destruction or free capacity on deletion. A durable release intent is committed before DELETE and reconciled by original PVC/PV UID after a lost response. A name-only legacy retry is rejected after a completed release and name reuse; an old UID can return its own retained record but never delete the replacement. Demo requests omit uid.
- GET /api/events: `{id,time,level,action,message,node}`

Kubernetes Go types live in `api/storage/v1alpha1`, shared with the Agent; HTTP handlers live in `internal/storage/httpapi`, following the same naming as `internal/pulsar/httpapi`. The Agent has no separate HTTP API or CRD group. The shipped Storage schemas live in `config/storage/crd`, one file per CRD; `make manifests` generates only Pulsar schemas in `config/pulsar/crd`. Storage CR/workload examples live in `config/storage/samples` and are not part of deployment bases. PhysicalDisk objects are reported by the Agent.

Production CRDs cluster-scoped group `storage.diskfleet.io/v1alpha1`: PhysicalDisk and DiskPool. DiskPool spec: `nodeName`, `devices: [{path,serial,sizeBytes}]`, `vgName`, `approved: bool`, `allocationApproval: {poolUID,runID,resultDigest,decision,reviewedAt,note?}`. The first approval permits device initialization; allocationApproval separately authorizes business capacity. status: phase, capacityBytes, availableBytes, message, observedGeneration, benchmark. Node label on objects `storage.diskfleet.io/node`. PhysicalDisk spec: nodeName,path,serial,sizeBytes,model,media; status: phase,reasons,poolName,lastObservedTime,validUntil,nodeUID. Exactly one disk per DiskPool/VG in initial release for failure isolation. Batch fleet enrollment is one pool per disk, not cross-node VG.

Go discovery uses `internal/agent/discovery.Discoverer.Discover`; the LVM backend is `internal/agent/lvm.Backend.EnsurePool`. Typed devices carry path/serial/sizeBytes, and pool results carry vgName/capacityBytes/availableBytes. A nonempty DiskPool UID is required and stored in the host journal as poolUID. Safe list-argv execution, per-host file lock, stable by-id identity, explicit approval, system/used-disk rejection, no wipe/delete, durable ownership. The Agent permits legacy Ready-journal migration only with independently verified pool/StorageClass ownership; the backend still verifies PV UUID, VG tag and single-disk membership before adding the UID, without initialization. `internal/storage/cluster` validates storage resource naming and ownership; node reconciliation and LVM writes belong exclusively to `internal/agent`.

Duplicate live DiskPool claims on the same node (VG, path or serial) are rejected regardless of node labels. The API projects these as Conflict with zero usable capacity and excludes their classes from trusted volume management, so legacy duplicate Ready records cannot double-count physical capacity.

Cluster integration in `internal/storage/cluster` reads/writes the Kubernetes API using explicit connection settings or a service account; it does not automatically load kubeconfig. The node Agent binary is `/usr/local/bin/diskfleet-agent` (`go build ./cmd/agent`) and runs one instance per selected node, using NODE_NAME and ENABLE_DISK_WRITES=false by default. `internal/storage/httpapi` owns HTTP delivery, `internal/storage/store` owns demo state and local plans/audit, and `web/src` owns the shared React console. Both Go services use `internal/kubeconfig` for connection configuration. The repository root owns Pulsar controllers, the React UI, image orchestration and the shared gateway configuration.

The Go Agent and Storage API have no direct HTTP/RPC connection. The resource API, field names, hashed names, finalizer, StorageClass ownership, and host journal format remain compatible. `config/storage/default` composes the Storage CRDs, RBAC and manager manifests; `config/agent/default` composes Agent RBAC and its DaemonSet. The Storage manager base owns the shared `diskfleet-system` namespace. `deploy/bundles/storage` composes both without Pulsar, and `deploy/bundles/all` composes all modules. Agent image is independent of the API image.

SQLite compatibility: `STATE_DIR/state.sqlite3` retains the original `objects`, `events`, and `plans` schema and JSON records, including `release-intents` and retained volumes. The pure Go SQLite driver uses WAL and immediate transactions. The Deployment mounts the independent `diskfleet-api-state` PVC and uses one replica with `Recreate` updates. Its filesystem must support SQLite WAL and local locking; keep consistent backups. API runtime is `/usr/local/bin/diskfleet-api`.

Successful Agent observations are valid for one configured reconciliation interval plus its maximum 20% jitter (default 30s interval, 36s validity). Scan failures do not renew observations; missing disks become Offline without changing their last successful observation. A report must satisfy `lastObservedTime <= now < validUntil`, and its `nodeUID` must identify the current Node. Upgrading the CRD and Agent is required before the new API admits old inventories to new plans. This adds optional status fields without changing immutable device identity or SQLite table formats.

The bounded `benchmark` report contains `poolUID,nodeUID,vgName,device,runID,profile,phase,startedAt,completedAt,testSizeBytes,workloads,cleanupVerified,errorCode?,message?,resultDigest`. Profile `temporary-lv-v1` uses a temporary 1 GiB LV, queue depth 16 and four workloads (`seq-write`, `seq-read` at 1 MiB; `rand-write`, `rand-read` at 4 KiB), each for at least 30 seconds. Each workload records `name,blockSizeBytes,queueDepth,durationSeconds,bytes,bandwidthBytesPerSecond,iops,latencyMeanNs,latencyP95Ns,latencyP99Ns,errors`. The SHA-256 digest binds the typed report excluding `resultDigest` itself. A future completion time, missing metrics, identity mismatch or unverified cleanup blocks review. Human review chooses suitability; the API does not invent a universal performance threshold.

Allocation states include `PendingBenchmark`, `Benchmarking`, `BenchmarkFailed`, `AwaitingReview`, `Rejected`, `AwaitingStorageClass`, `Approved`, `LegacyUnreviewed` and `Blocked`. A legacy Ready pool without a report remains observable but cannot receive new allocations or a retroactive approval while its StorageClass exists. Existing volume observation, ownership restrictions, expansion and Retain recovery remain independent of this new-allocation gate. No automatic retest or StorageClass deletion is performed. Demo reports explicitly identify simulated values; preseeded demo pools carry simulated approvals, and new demo pools require review.

Fleet planning and the exported StorageClass renderer require the same full benchmark/approval evidence, explicit initialization approval, no deletion timestamp, and never override an API snapshot with `canCreateVolume=false`. Offline JSON remains untrusted input and cannot verify live cluster identity. Historical StorageClass observation deliberately keeps the old ownership/configuration verifier so adding the allocation gate does not hide existing volumes. CSI itself does not read DiskPool approval: the controller withholds newly managed pool StorageClasses until approval; administrators must separately prevent broad or externally created classes from selecting unreviewed VGs.
